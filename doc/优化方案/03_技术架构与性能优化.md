## 当前架构核心问题

每个 Tauri command 独立执行 `System::new()` → `refresh_xxx()` → 返回（[lib.rs L148-149](../../src-tauri/src/lib.rs)）。无共享状态、无缓存、无定时推送。sysinfo CPU 使用率需两次采样差值，首次 refresh 恒返回 0。前端从未调用这些命令，使用 `Math.random()` 代替。

## 推荐架构：单例采集器 + 事件推送

```
前端 useSystemMonitor() ← listen("sys://metrics")
前端 useProcessStore()  ← listen("sys://processes")
操作类命令仍用 invoke（kill/cleanup/scan）
        ↕ Tauri Event Bus
后端 MonitorService (tokio::spawn 定时循环)
```

### R3 补充 · 一次性采集路径与"三步暖机"（2026-09-22 实测，缺陷编号 H-06）

上面那张表只覆盖**循环式**采集（有常驻 `System`，两帧之间天然有间隔）。T5-04 引入的排行/兜底路径是**一次性**采集：现造一个 `System`、要在一问一答里就给出真实 CPU —— 这类路径在 macOS 上有 **3 次触碰**才拿得到每进程 CPU，不是 2 次：

1. 建表（`refresh_processes*` 第一次：登记进程、此时 `total_existing_time` 还是 0）
2. 填基准（第二次：写 `old_utime/old_stime`，但 `cpu_usage` 仍算不出）
3. 取差值（第三次：`compute_cpu_usage` 要求 `total_existing_time > 0`，才给出真实百分比）

`System::new()` 只做第 1 步（构造时不采样），所以"new → refresh → 读"这条看起来最短路的写法**恒得 0.0**；`System::new_with_specifics(...)` 把第 1 步挪进了构造，于是"构造 → 留间隔 → refresh"两步就够。本机实测向量（**同一形状**：造一个 `System`，之后每 300 ms 做一次进程 refresh，取三轮读数）：

| 构造方式 | 每进程 CPU 读数 |
| --- | --- |
| `System::new()` | `[0.0, 0.0, 113.2]` |
| `System::new_with_specifics(RefreshKind::nothing())`（不带任何进程项） | `[0.0, 0.0, 106.2]` —— 与上一行**同形** |
| `System::new_with_specifics(nothing + 进程窄口径)` | `[0.0, 105.6, 110.3]` ✓ |
| `System::new_with_specifics(RefreshKind::everything())` | `[0.0, 104.4, 107.4]` —— 数值也对，但口径不可接受（见下） |

这张表推翻了一个看起来合理的猜测：**决定性的不是"采样项里有没有 CPU"，而是"构造时有没有完成建表那一次触碰"** —— `RefreshKind::nothing()` 与 `System::new()` 给出一模一样的 `[0, 0, 真值]` 形状，而带进程项的构造自带建表，于是第二轮就能出数（第四行用宽口径也一样出数，出不出数与宽窄无关）。

结论有两层，第一层是"暖机顺序"，第二层更重要：**采样口径必须由代码收口，不能留在注释里**。修法是把一次性采集压成唯一两个函数，任何调用点都无法把三步走错：

```rust
// src-tauri/src/monitor.rs
pub fn process_refresh_kind() -> ProcessRefreshKind   // nothing().with_memory().with_cpu()
pub fn process_system() -> System                     // new_with_specifics(nothing + 上面的 kind)
pub fn collect_processes_warmed(q: &ProcessQuery) -> ProcessPage  // 建表→填基准→WARM_SAMPLE_MS(260ms)→取差值
pub fn collect_top(by: ProcessSort, limit: usize) -> Vec<ProcessInfo>  // = collect_processes_warmed，Agent 用
```

同一轮把口径钉死，并且**订正了一处写错的注释**：旧注释说 `refresh_processes()` 的默认口径"连带读命令行参数与环境变量"，这不对 —— 查 sysinfo 0.33.1 的 `common/system.rs`：`refresh_processes()` 等价于 `nothing().with_memory().with_cpu().with_disk_usage().with_exe(UpdateKind::OnlyIfNotSet)`，里面**没有** `cmd`/`environ`；会把参数和环境变量读进来的是 `ProcessRefreshKind::everything()`（它的 `cmd`/`environ`/`cwd`/`root` 全是 `OnlyIfNotSet`）。所以"不采集命令行参数与环境变量"这条口径此前**并没有被违反**，被多读的是 `disk_usage` 与逐进程的可执行路径 —— 仍然不该读，但不能记成一笔没发生的账。真正的隐患在那类"口径由依赖决定"的写法：默认口径会随 sysinfo 升级而变，注释却不会跟着变。现在所有循环/一次性路径统一走 `refresh_processes_specifics(..., process_refresh_kind())`（显式两项：memory + cpu），只有进程详情抽屉那一条路径用 `detail_refresh_kind()`（在 `exe` + `cwd` 上显式放宽，`cmd`/`environ` 仍一律不读；顺带修掉"工作目录永久显示 `—`"，因为原来的窄口径里根本没有 `cwd`）。回归由三条测试把住：`per_process_cpu_is_actually_sampled`（起一条 burn 线程、用自身 PID 当关键字，断 `cpu_usage > 0.0` **且** `memory_bytes > 0`，防止"只暖了 CPU 而内存无来源"这种半对）、`process_detail_exposes_paths_but_never_command_line_or_env`、`agent_ranking_collection_returns_ordered_rows`。

**Agent 侧的调用形态**（`commands.rs` 的诊断 Agent 分节，L282–357）：`agent_query` 是 `async` 命令，260 ms 的暖机经 `tauri::async_runtime::spawn_blocking` 挪出 IPC 线程（与 `scan_junk_files` 同款先例），CPU/内存两张排行榜在 blocking 线程内用 `std::thread::scope` 并发取（各自独立 `System`，两榜合计仍约等于一榜耗时），且只有 `rankProcesses` / `diagnoseSlowness` / `memoryPressure` 三个意图会触发（`rank_needs`）—— 问"磁盘还剩多少"不付这笔钱。**刻意不复用进程表的缓存页**：那一页带着用户当前的关键字和页码，拿它排行会把"当前这 30 条里最高"说成"整台机器最高"。

规划的两个 `stores/` **没有落地，也不打算落地**：`zustand` 已随 `src/agent` 死代码一并移除，而这两处实测各自只有 `App` 一个消费者 —— 为一个消费者重新引状态库，换来的只有"多一条要手工保持同步的链路"，故改为自定义 hook 收口（决策依据与逐条实测见 [05 的 T4-02/T4-03 行](./05_实施路线与任务拆解.md) 与 [06 的 GUI 实测](./06_测试验收与风险清单.md)）。T5-11 的偏好导入/导出**确实吃到了这个单点红利**：落地时只加了 `buildPrefsSnapshot()`/`applyPrefs()` 两个函数，导出侧没有第二个序列化点，导入侧的整份替换也只是调回既有那 5 个 setter —— 于是"五项一起落盘"由结构保证，不存在"界面变了、localStorage 还是旧的"这种中间态（实测覆盖的是 `interpretImportedPrefs` 的 13 条值语义断言 + 一次真实 IPC 写出/读回，见 06；单独再验一次 localStorage 写入面没有做，因为写路径就是既有的那 5 个 effect，本次未改动）。
