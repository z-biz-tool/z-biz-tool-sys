| 原则 | 说明 |

| **夹具使用 mock 系统数据** | 所有测试使用预构造的 MetricsSnapshot / ProcessInfo 夹具，**不碰真实进程、不执行真实 kill、不删除真实文件** |

1. **debug 二进制的 `../dist` 是编译期内嵌的** —— 产物编译好之后再改 `dist/index.html` 或往 `dist/` 放文件都无效（第一轮就是"以为注入了其实没有"）。要么在 `cargo build` 之前注入，要么走 devUrl。

4. **antd Tabs 的面板切走后仍挂在 DOM 里** ⇒ 全局 `document.querySelector` 会命中别的页签的表格（有一轮 `e06` 读到"没有匹配的进程"就是这个原因）。要先按卡片标题定位（`cardBy("大文件扫描")`）再往下查。

### FI-01~FI-04 故障注入的补做事实（2026-09-22 23:44–23:52）

**先记下这轮最重要的一条：我自己新写的代码被自己的探针抓到 bug。** 恢复函数最初写成 `reason: &(dyn Any + Send)`，调用处传 `&panic_reason(&payload)`（payload 是 `Box<dyn Any + Send>`）—— 这会让 downcast 看到的是**盒子而不是盒子里的内容**，于是一条正常的 `panic!("…")` 也会被打成"未知 panic"。是我加的 `fi03_probe_what_a_panic_payload_actually_carries` 把载荷形状打出来才看清：

| 载荷来源 | `downcast_ref::<String>()` | `downcast_ref::<&str>()` | `{:?}` |
|---|---|---|---|
| `panic!("注入：字面量")` | `None` | `Some("注入：字面量")` | `Any { .. }` |
| `panic!("注入：{}", 42)` | `None` | `Some("注入：42")` | `Any { .. }` |
| `panic_any(42u32)` | `None` | `None` | `Any { .. }` |

⇒ 三条事实：① 载荷只能按 `&str` 取（`String` 那条在这条工具链上一直是 `None`）；② `Debug` 只会打 `Any { .. }`，所以"兜底用 `{:?}`"等于永远读不到原因；③ `panic!(42u32)` 在这个 edition **根本编不过**（`format argument must be a string literal`），非字符串载荷只能由 `panic_any` 产生。修法：`panic_reason` 与两个恢复函数都**按值收 `Box`**，并把"读不到就说读不到"这句留在注释里。测试侧同时断言恢复时拿到的原因含注入标记（`reason.contains("注入")`），否则日志会静默退化成空话。

### CI 改造（T5-09 已落地 2026-09-22，原规划见下）

实际落地的是**新建** [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)（不改建 build.yml：那条链一跑就会创建 draft release，把它塞进 PR 门禁等于每次评审都产出一个发布物），三条腿 macos-latest / ubuntu-22.04 / windows-latest × 11 步（`npm ci` → `tsc` → `npm run build` → `cargo test --lib` → `cargo clippy --all-targets` → Intel 交叉 `cargo check`）。与上面那段规划有三处**有意分歧**：

1. `cargo test --all` → **`cargo test --lib`**：与本机门禁基线逐字一致，且 `--all` 会连带编译 examples/benches 里规划过但从未落地的 `criterion` 基准。
2. `npm run test -- --run` → **删掉这一步**：`package.json` 的 scripts 里根本没有 `test`（只有 dev/build/preview/tauri/typecheck/format），lockfile 里 `vitest` 命中 **0** 条 —— 照规划写就是一条必然红的步骤。前端侧改为 `npx tsc --noEmit` + `npm run build`（后者的 script 本身就是 `tsc --noEmit && vite build`，拆开是为了让失败信号分清"类型错"还是"打包错"）。
3. `cargo clippy -- -D warnings` → **不带 `-D warnings`**：`-D warnings` 只在"已经见过全部平台的 warning 集"时才安全；本机是 macOS，Linux/Windows 必然带出平台特有的（例如只在 `cfg(unix)` 下被调的 helper 在 Windows 上算 `dead_code`），而这些输出我在本地一条都看不到。先让它们以 warning 呈现，等 CI 跑过一轮、把清单收齐后再升级成门禁。

规划里没写、但实现时被源码逼出来的硬约束：**`npm run build` 必须早于任何 cargo 步骤**。`dist` 在 `.gitignore` 里，`tauri-codegen/src/context.rs` 见 `frontendDist` 目录不存在就 `panic!`，而展开点是 `src-tauri/src/lib.rs:62` 的 `tauri::generate_context!()` —— 顺序错了连 `cargo test` 的编译阶段都进不去。

**触发面刻意是 `pull_request` + `workflow_dispatch`，没有 `push`**：本仓有直接往 main 推 WIP 的习惯（`gh run list` 里 build.yml 的 6 次 dispatch 就是证据），加 push 触发会让每次 WIP 占满三条腿。`permissions: contents: read`（该 job 不建 release、不传产物）。
