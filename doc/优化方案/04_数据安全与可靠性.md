## S1 · 危险操作分级与确认

| 级别 | 操作 | 确认方式 | 当前 |
|------|------|----------|------|
| L3 致命 | kill 系统进程（PID≤100 / 保护列表） | **禁止**，按钮灰显 | ✗ 无限制 |
| L2 高危 | kill 用户进程、清理 Risky、删除启动项 | Dialog + 输入名称验证 | ✓ kill 走 `validate_kill` + Modal；启动项三项操作全部要求逐字输入名称（2026-09-23 T3-08） |
| L1 中危 | 清理 Safe/Moderate、DNS 刷新、禁用启动项 | Popconfirm | ✓ 清理有确认对话框（T3-10）、DNS 有 Popconfirm；启动项**刻意不低于 L2**：禁用同样要逐字输入名称 |
| L0 只读 | 查看监控、扫描、枚举 | 无需确认 | ✓ |

### cleanup 加固

### 启动项操作（T3-08，2026-09-23 落地）

实现落在 `src-tauri/src/startup.rs`（生产段 1–524 行 / 24 174 B，`cargo test --lib startup::` 22 条）。方案原句只写了"备份 + 输入名称确认"，实际边界更多，每一条都有单测：

- **前端只提交 `id` 与名称，永不提交路径。** `id` 必须形如 `<来源前缀>-<一枚文件名>`：含 `/` `\` `\0`、或是 `.`/`..` → `PATH_DENIED`。可操作来源只有一张白名单表（macOS 仅 `~/Library/LaunchAgents`、Linux 仅 `~/.config/autostart`、Windows 表为空 ⇒ 任何 id 一律 `UNSUPPORTED`），`LaunchDaemons` 与全局 `/Library/LaunchAgents` 需要 root，绝不出现在表里。
- **禁用与删除都只是"一次移动"。** 模块里唯一动文件的原语是 `fs::rename`：原件移入 `app_data_dir()/startup-backup/<prefix>/`（删除多一层 `out/`，目录懒创建）。生产段 0 处 `fs::remove_file` / `remove_dir` / `Command` / `osascript`，由 `the_module_never_deletes_a_startup_file_it_was_asked_to_move` 做源码文本审计。两者差别只在**是否仍被列出**：禁用后仍在列表里、可一键恢复（`listed: true`）；删除后不再列出，但字节仍在 `out/`（`listed: false`，message 里如实给备份位置）。
- **绝不覆盖。** unix 的 `rename` 会静默顶掉同名目标文件，丢的是上一份备份，所以落点已有同名文件时先拒（`INVALID_INPUT`）。
- **逐字确认，且在搬运之前。** `require_confirm` 要求提交名称与文件名**完全一致** —— 少一个字符、多一个空格、换大小写都拒；它跑在 `resolve` 之后、任何 `rename` 之前，所以被拒时文件没离开原位、备份目录不会多出东西。
- **只认真通规文件，且判定作用在未解析路径上。** 这一条是本轮实测抓出来的**真 bug**：原实现把 `entry_is_plain_file` 判在 canonical **之后**，于是"指向同目录另一份 plist 的链接"被看成合法启动项，"禁用 `alias.plist`"实际搬走的是邻居的**真身**、还改名成链接名，原地只剩一个断链（dotfiles 仓库常这么摆 plist）。现改成判 canonicalize 前的候选路径（放在 canonicalize 之后是为了让"根本不存在"仍报 `NOT_FOUND` 而不是"不是普通文件"），并与列表侧同一口径（`entries()` 也不列链接）。
- **不解析内容、不承诺系统级效果。** 不读 plist 的 `Disabled` 键，`enabled` 只表示"文件此刻在不在启动目录里"；界面的 `Alert`、确认框文案与 message 都按这个说法写，避免把"移动了文件"讲成"系统已禁用该服务"。
- **不给不可操作的来源留按钮。** `StartupItem.operable` 由唯一的 `id_is_operable()` 打标，`cleanup.rs` 只借它给 Login Items / 注册表 / systemd 三类打 `false`，界面据此显示"不支持在此操作"标签而不是按钮 —— 两边各判一次就会出现"按钮点得下去、后端回 UNSUPPORTED"。

## S2 · 采集不泄漏敏感信息

| 字段 | 风险 | 处理 |
|------|------|------|
| 进程名 | 低 | 原样展示 |
| 完整路径 | 中（暴露用户名） | 默认仅 basename；详情面板展示全路径 |
| 命令行参数 | **高**（`--password=xxx`） | 默认不采集；开启后对 `password|token|secret|key` 模式脱敏为 `***` |
| 环境变量 | **高** | 不采集、不展示 |

> **采样口径的可证化（2026-09-22，随 T5-04/05/06 一并）**：上面两行"不采集"过去只写在注释里，代码走的是 sysinfo 的**默认**进程刷新口径。查 sysinfo 0.33.1 的 `common/system.rs` 逐条核对后如实记账：`refresh_processes()` = `nothing().with_memory().with_cpu().with_disk_usage().with_exe(OnlyIfNotSet)` —— **不含** `cmd`/`environ`，所以"不采集命令行参数与环境变量"这条口径**从未被违反**（这一点此前的一份代码注释写错了，把 `ProcessRefreshKind::everything()` 的行为安到了 `refresh_processes()` 头上，本轮已订正）；被多读的其实是 `disk_usage` 与逐进程的**可执行路径**，属于本文"完整路径 = 中风险"那一档。真正的风险是"口径由依赖决定"：默认口径随版本变，注释不会跟着变。现在 `monitor::process_refresh_kind()` 把要读的东西显式列成两项（memory + cpu），全项目的循环与一次性采集都经 `refresh_processes_specifics` 走它；**唯一**放宽处是进程详情抽屉的 `detail_refresh_kind()`（多加 `exe` + `cwd`，正是表中"详情面板展示全路径"那一行所要求的；`cmd`/`environ` 仍不读）。回归：`process_detail_exposes_paths_but_never_command_line_or_env`（详情里有路径、但没有参数与环境）、`per_process_cpu_is_actually_sampled`（窄口径下 CPU 仍为真值，防止用"不采集"当借口把 CPU 也关掉）。

### 持久化最小化

进程快照、命令行参数**不持久化**。仅持久化：用户偏好（localStorage）、历史趋势（聚合数据）、告警记录、Agent 对话（脱敏后）。

> **落地对账（2026-09-22，T5-03）**：白名单目前恰好三项有实现 —— ① 用户偏好 = `localStorage`（**5 项**，读侧过白名单；第 5 项是 T5-01 的告警阈值，此前本文写"4 项"未同步）；② 历史趋势 = `<app_data_dir>/history/points.jsonl`（聚合后的 CPU/内存/网络速率点，无进程信息）；③ **告警记录 = `<app_data_dir>/alerts/alerts.jsonl`**（字段仅 `metric/level/value/threshold/target/consecutive/timestampMs`，同样不含进程名与命令行）。告警的 `target` 是挂载点/网卡名这类本地路径，**只在写盘副本上**过 `log_sanitize::sanitize`（会话内推送保留原值以便界面显示），落盘字段就这 7 个、不带任何进程名或命令行 —— 与本文的脱敏口径一致，验证见 [06](./06_测试验收与风险清单.md) 的 `persisted_alert_targets_are_sanitized_while_the_event_itself_is_not`。

> **表中"Agent 对话（脱敏后）"这一项：T5-04/05/06 落地后刻意**不**需要落盘（2026-09-22）**。原方案假设 Agent 是多轮对话、要有历史，所以预留了"脱敏后持久化"；实际形态是一问一答、`Reply` 里不留任何会话状态，界面也不做历史列表（见 02 的 F8）——于是这一项**当前落盘面为零**，不需要开新的文件，也就不需要新的脱敏口径。若将来真要存对话，必须先回到本文这一节补口径（用户问题里可能含路径/进程名，`log_sanitize` 对自由文本的覆盖未经检验），而不是顺手 `fs::write`。

> **T5-11 新增的落盘面（2026-09-22）**：偏好导出会把那 5 项偏好写成一份 JSON 到**用户手选的路径**，这是上表白名单之外的一次外写，因此单独立了 SEC-V11 这道闸。内容口径：`buildPrefsSnapshot()` 只取 `darkMode/intervalMs/trendRangeSecs/activeTab/alert`，**不含任何路径、进程、主机名或 IP**（真机导出实测 508 B / `keys=5`，见 06）；导入是"预览 → 应用"两步，且值语义只在浏览器一处判 —— 后端把 `prefs` 当不透明 JSON，免得出现两套合法性口径。

## S3 · 只读监控优先

监控采集链路（metrics/processes/disks/networks）**永远只读**，不修改系统状态。

**DNS 刷新去 sudo 方案**：

| 平台 | 方案 | 备注 |
|------|------|------|
| macOS | `dscacheutil -flushcache`（macOS 12+ 无需 sudo） | 若需 `killall mDNSResponder` 则提示用户手动 |
| Linux | `resolvectl flush-caches`（用户级） | 无 systemd-resolved 时返回明确错误 |
| Windows | `ipconfig /flushdns`（已正确，无需管理员） | 保持现状 |

**绝不**在应用内调用 `sudo`。失败时返回可复制的手动命令。

## S4 · Agent 安全边界

**核心原则：Agent 只建议，不执行。**

| 能力 | Agent 可调用 | 需用户确认 | 禁止 |
|------|:---:|:---:|:---:|
| 读取 metrics/进程/磁盘/网络 | ✓ | | |
| 终止进程 / 清理 / 禁用启动项 / DNS | | ✓（走 S1 流程） | |
| 执行任意 shell / 修改系统配置 / 访问其他用户数据 | | | ✗ |

- Agent 建议必须匹配预定义操作模板，自由文本命令一律拒绝
- Agent 上下文不注入环境变量、SSH 密钥、Cookie 等敏感内容
- 建议渲染为"待确认卡片"，用户点击"执行"才触发正常安全流程

> **落地对账（2026-09-22，T5-04/05/06）—— 比本表更窄，且最后一行的措辞已修正**：
> ① 上表第三行的"点击'执行'才触发"**不是**实现形态：实现里**没有执行按钮**，卡片上的动作只有"打开某页签"和"在进程表里定位某个 PID"两种导航。原句会让人以为存在一条"点了就走到 S1 流程"的通路；实际是用户点完只是**到了那个页面**，还得在那里自己点、自己确认，才由既有的 `kill_process` / `cleanup_junk_files` / `flush_dns_cache` 各自过 S1 的校验。这样"Agent 的输出"与"能改变系统状态的那次调用"之间隔着**至少两个独立代码路径**，而不是一个确认弹窗。
> ② 建议词汇表由类型系统封死：`Suggestion` 是 serde internally-tagged 枚举，只有 `OpenTab{tab}` / `FocusProcess{pid,name}`；`Reply.executed` 是**私有字段且构造恒 false**，前端拿不到可以自己改的地方（`every_reply_is_marked_not_executed`）。
> ③ "上下文不注入敏感内容"这一条的实现是**根本不建上下文**：引擎入参只有 `Option<&MetricsSnapshot>` + 两份进程榜 + 告警配置，采集侧连 `cmd`/`environ` 都不读（见 S2 的口径可证化），SSH 密钥/Cookie 无从进入。
> ④ "自由文本一律拒绝"由 `COMMAND_LIKE` 表 + `free_text_command_requests_are_refused` 把住，命中即 `refused=true`、只回"去对应页面，那里有确认步骤"，**不生成任何命令文本**。
> ⑤ 四条可执行的守卫全在 `cargo test --lib`（本仓唯一有 CI 门禁的语言侧）：`agent_module_has_no_destructive_call_path`（扫引擎生产切片）、`agent_command_section_has_no_execution_path`（自己按分节注释定位 `commands.rs` 的诊断 Agent 分节，禁止 `kill_process`/`cleanup_junk_files`/`flush_dns_cache`/`Command::new`/`std::process::`/`std::fs::remove`/`std::fs::write`/`sudo`，同时**要求**出现 `agent::answer` 与 `monitor::collect_top`，防止把执行逻辑藏进看不见的 helper）、`agent_panel_has_no_ipc_channel_of_its_own`（从 `CARGO_MANIFEST_DIR` 读**前端** `AgentPanel.tsx`，禁 `@tauri-apps/api`/`invoke`/`fetch`/`localhost`）、`reply_serializes_no_executable_payload`（把 Reply 走成 JSON 后递归遍历所有 key，出现 command/args/shell/script/path 类字段名即失败）。另加 `suggested_tabs_are_all_real_page_keys` 保证建议里的目标页签真实存在。
> ⑥ 未扩 capabilities（仍是那份 8 条显式清单，见 SEC-V02）、未新增 `AppError.code`、未新增落盘文件。

## S5 · Tauri 权限收敛

### capabilities 改造（规划）

```json
{
  "permissions": [
    "core:default", "core:event:default", "core:event:allow-listen", "core:event:allow-emit",
    "dialog:default", "dialog:allow-message", "dialog:allow-ask", "dialog:allow-confirm",
```

**移除**：`fs:default`、`fs:allow-read`、`shell:default`、`shell:allow-execute`。前端无需直接文件/shell 访问，全部走后端 command。

**插件精简**：移除 `tauri-plugin-shell`、`tauri-plugin-fs`；新增 `tauri-plugin-notification`。

### CSP 启用（规划）

Ant Design CSS-in-JS 需 `'unsafe-inline'`；Recharts inline SVG 需 `data:`。

## S6 · 可靠性设计

### 错误处理统一（规划新增 `src-tauri/src/error.rs`）

```rust
pub struct AppError { pub code: String, pub message: String, pub detail: Option<String> }
```

### 采集器容错

| 故障 | 处理 |
|------|------|
| refresh 失败 | 返回上次缓存 + `stale: true` |
| 进程枚举部分失败 | 跳过失败项，不中断 |
| 磁盘不可达 | 标记 `available: false` |
| 前端未 listen | emit 静默忽略 |
| 采集循环 panic | catch_unwind + 重启 |

### 清理操作

- 清理前生成 manifest（JSON）
- 逐文件删除，失败记录 errors（已实现 [cleanup.rs L299-303](../../src-tauri/src/cleanup.rs)）
- 新增 CancellationToken 支持中断
- 文件删除不可逆，中断后已完成部分不回滚
